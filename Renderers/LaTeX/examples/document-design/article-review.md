# 目标与边界

文档工具需要把可维护的源文件转化为可阅读、可检查的成品。一次成功运行不仅意味着进程返回零，还意味着内容完整、字体可用、资源正确，并且读者能够辨认正文中的层次。

本文把设计范围限制在本地构建：作者提供 Markdown、元数据和实际素材；构建器完成转换与排版；验收者检查日志及页面。远程协作、在线编辑和自动发布不在范围内。

## 短文与长文是不同的版式

一份两页的技术说明不应先花两页展示封面和目录。Article 的第一页应尽快交代标题、作者、摘要与正文，后续页面则用克制的页眉帮助读者定位。Book 更适合分章组织的大文档，可以保留独立封面、目录和章节首页。

两者可以共享字体、颜色和语义组件，但不应共享所有起始行为。版式选择负责结构，主题负责视觉风格；把二者分开，才能避免“换一种颜色却仍然像一本书”的问题。

# 构建阶段

## 输入与配置

首先解析元数据，验证文档类型、标题区形式、纸张和字体配置。明确指定的无效值应直接报告，而不是悄悄退回某个默认值。对于可选字段，只在缺省时选择合理默认。

本地资源也在这一阶段建立边界。图片应有明确来源，路径不能越过允许的目录；缺失文件需要指出名称。临时构建目录不应成为任意读取其他文件的理由。

## 语义转换

转换器应保留标题、公式、图表和题目的实际含义。展示为一个框还是普通正文是视觉决定；删除答案、改变编号或忽略选项则是语义决定，必须有明确配置和验证。

例如，学生版的答案不应仅用白色文字藏在 PDF 中。更可靠的做法是在生成排版源文件之前就去掉答案内容，再检查导出文本中是否仍然存在。这使视觉检查与内容检查能够相互补充。

## 排版与输出

在临时目录中完成排版，确认生成文件可用之后再替换目标成品。如果转换或编译失败，保留上一份有效输出。这个约定可以避免一次错误编辑把可交付版本覆盖成半成品。

```python
def publish_result(candidate, target, validate):
    validate(candidate)
    candidate.replace(target)
```

这段代码只表达阶段顺序。实际实现还需要处理目标路径验证、同一文件系统内替换、权限错误以及失败时的临时文件清理。

# 验收方法

::: {.table #acceptance kind="comparison" caption="不同证据检查不同问题"}
| 证据 | 可以检查 | 不能单独保证 |
| --- | --- | --- |
| 返回码与日志 | 编译失败、缺字、部分溢出 | 视觉效果与内容正确性 |
| 导出文本 | 标题与末段是否保留 | 图片清晰度与元素位置 |
| 页面尺寸与页数 | 纸张、额外空页 | 换行是否自然 |
| 页面截图 | 重叠、留白、阅读层次 | 所有隐藏内容是否移除 |
:::

## 使用可复现的小样

针对每一种重要行为保留最小样例。单页短文用来检查首页是否浪费空间；多页短文检查续页页眉和段落完整性；长标题检查自然换行；跨页表格与提示框检查内容是否被截断。

测试数据不需要来自私人课程或真实客户材料。用公开、合成的输入就可以覆盖大部分结构行为；私人样本用于本地验收，不混入工具仓库。

::: {.note title="页数不是唯一指标"}
把文档从三页压成两页，不一定改善体验。如果代价是字号过小、行距过紧或者表格难读，应保留更多页面。验收应同时考虑内容完整性和正常阅读尺寸下的可读性。
:::

## 比较配置，而不是比较偶然输出

字体和纸张改变后，换行与分页都可能变化。比较前应记录源文件、主题、字体、工具链和构建命令。对需要长期维护的文档而言，能够解释为什么发生变化，比偶然得到一次漂亮结果更重要。

# 已知限制与后续工作

日志检查无法覆盖所有视觉问题。绝对定位的元素、图片内部的文字和复杂公式，仍需要人工观察。字体也会影响中英文的视觉重量，不能仅凭“都能显示”就认定搭配合适。

下一步应优先收集真实阅读反馈：读者能否快速找到结论，长段落是否疲劳，表格与 Box 是否打断阅读。只有当这些问题明确后，再增加新的装饰或布局选项。

本示例到此结束；它的标题与摘要只出现在开头，续页使用短页眉，正文按可用空间自然分页。
